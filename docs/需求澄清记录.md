## 二、已确认决策

### （一）第一轮澄清（2026-11-20）

### 1. 下单流程与订单模型

- PRD 开头总述中的流程描述（"用户下单→陪玩应单→用户选人&付款→陪玩接单"）**说法错误，作废**。
- 正确流程：**用户选人（可多人）→ 选择并填写需求、付款 → 陪玩开始 → 陪玩结束**。
- "应单"发生在选人阶段：
  - 指定单：老板选人本身即基于陪玩可接单状态；
  - 公开派单：陪玩在 120 秒窗口内点击应单，老板在应单列表中选人。
- **多陪玩订单的数据形态**：每个陪玩生成一条**独立订单数据**，仅在 UI 层合并展示方便老板操作；各订单可独立处理开始、结束、评价、退款。
- 订单结束动作：**陪玩先点击结束 → 老板确认**。

### 2. 计价规则

- 总价 = Σ（每个陪玩的单价 × 数量），数量单位为小时或局。
- 陪玩单价维度：**陪玩等级 × 陪玩模式**，具体数值由管理员在后台填写（结合所属游戏板块查询）。
- 加价项：在"单价 × 数量"基础上**简单相加固定金额**，多个加价项**可叠加**。
- "一陪二/一陪三/一陪四"：含义为一个陪玩陪多个老板，仅作为**标签层面**处理，系统不核查实际人数。
- "时间段"：表示老板**预约**陪玩的服务时段，不一定立即开始。

### 3. 订单异常与退款

- 付款后陪玩在规定时间内未开始服务：老板可选择
  - 继续等待（重新计时一个相同时长）；
  - 放弃等待 → **退款星星到老板账号**。
- 陪玩付款后点击**拒绝服务**：直接全额退款星星到老板账号。
- 公开派单：本质是选人阶段，派单窗口时长（默认 120 秒）后台可配；超时后老板可重新发起。
- 等待时长、派单窗口时长均为后台可配置项。

### 4. 钱包、代币与抽佣

- 小程序内消费全部使用虚拟代币"星星"，非人民币；汇率可配置。
- 老板充值：
  - iOS 平台：1 人民币 = 7 星星；
  - 其他平台：1 人民币 = 10 星星。
- 陪玩提现：1 星星 = 0.1 人民币。
- 平台抽佣比例可配置（示例 15%）：老板支付 100 星星，陪玩实际到账 85 星星；订单服务与礼物送礼适用同一套抽佣逻辑。【2026-11-23 修订：抽佣算法不变，但订单、礼物拆为两个独立配置项，见第二轮 P1-1】
- 星星不会过期。

### 5. 账号体系

- 登录方式：兼容**微信快捷登录**与**短信验证码登录**。
- 允许**游客**浏览陪玩等无需身份的信息。
- 陪玩是普通用户之上的附加身份，陪玩也可以作为老板消费。
- 陪玩入驻、考核、升级均在后台管理页面操作。
- 注销条件：需先提现全部星星（仅陪玩收入余额可提；老板余额不可提，见第二轮 P0-2）；有进行中订单的，等待订单结束后才可注销。
- 注销后数据**直接删除**。【此条已被第二轮 P0-3 替代：注销＝个人信息匿名化＋置注销标记＋禁止登录，业务与财务数据依法保留，不再物理删除】

### 6. 亲密度

- 命名统一为"亲密度"。
- 计算依据：**已正常结束的订单金额 + 礼物金额**的总值，按可配置的换算比例计算。
- 发生退款时，亲密度连带扣减更新。

### 7. 实时通信与在线状态

- 实时通信采用**腾讯云 IM**。
- 陪玩**手动上报**当前是否在线（告知后端）。
- 陪玩自行标记在线但实际处于后台/离线而错过派单推送的，一期不做补救措施（不做高频微信/短信提醒，避免平台风控）。

### 8. 个人主页信息可见性

- 一期方案：由**后端代码决定字段是否返回**（不在前端做字段级配置），即字段可见性规则固化在后端。

### 9. 第一轮 P1 项结论

1. **排行榜口径**：完成订单才上榜；退款扣减相应亲密度；按中国时区；定时任务计算；分数并列时不区分顺序。
2. **隐私号**：老板设为隐私号（全局开关）后仍占榜单名额，匿名显示为"老板"（匿名文案可配置）；陪玩不允许设隐私号。
3. **系统播报**：仅对**赠送礼物**做循环播报，频率可配置；星星为虚拟代币，金额无需脱敏。
4. **礼物**：一期不做专属礼物、不区分礼物等级；一次送礼只能选一种礼物，**数量可多个**；礼物墙展示收到该礼物的个数。
5. **恋人关系 / Tag**：恋人关系由老板发起、陪玩确认；双方均可解除，无冷静期。Tag 不允许在陪玩有订单时操作；若异常发生，进行中的订单继续完成。
6. **客服派单**：本质是老板通过聊天让客服代发选人需求，派单链接有效期与自己公开派单一致。
7. **搜索**：系统 ID 从 10000 递增；昵称模糊匹配；重名不特殊区分，靠头像和 ID 辨别。
8. **默认 5 星评价**：触发期限后台可配置。
9. **点单须知**：先展示总须知，再展示板块须知与其他须知；老板的知悉动作需要**留痕**。

### （二）第二轮澄清（2026-11-23，问题原文与答复见第五节）

10. **充值通道与合规（P0-1）**：确认一期接入**微信小程序虚拟支付（米大师）**，iOS 侧虚拟代币充值必须走该通道；需尽快核实小程序服务类目可开通虚拟支付，该项为**上线阻断项，最早推进**。
11. **老板余额与账号注销（P0-2、P0-3）**：
    - 老板余额（充值余额）**不可提现、不可老板间转账**，只能通过下单、送礼消耗；注销时余额作废，并写入用户协议。
    - 账号注销 ＝ **个人信息匿名化 ＋ 置注销标记 ＋ 禁止登录**；订单、评价、礼物、财务凭证等业务数据保留，依法留存（网络日志 ≥6 个月、交易凭证 ≥5 年）。【替代第一轮"注销后数据直接删除"】
12. **钱包建模与陪玩一期限制（P0-4）**：钱包按**充值余额 / 收入余额**两个字段分户记账，流水记录抽佣明细；一期陪玩角色**隐藏充值入口与充值余额、拦截点单等老板专属行为**（数据结构先行支持，入口后续开放）。
13. **订单状态机异常分支（P0-5）**：
    - ① 付款后、陪玩开始前，**老板可主动取消订单**，取消后星星原路退款；
    - ② 陪玩点结束后老板超期不确认，超过配置天数**系统自动确认**；
    - ③ 服务进行中陪玩失联/中途停止，老板把订单号发给客服，客服核实属实后在后台操作**强制退款**（操作人、原因留痕）。
14. **一期功能边界（P0-6）**：**装扮商城、消费积分、访客与足迹、邀请好友奖励、关注/粉丝**一期全部不做，不建表、不留空心字段。
15. **抽佣配置拆分（P1-1）**：订单抽佣与礼物抽佣拆为**两个独立配置项**（算法一致、配置独立，预留差异化空间）。【替代第一轮"同一套抽佣逻辑"的单配置表述】
16. **预约时段规则（P1-2）**：预约单**允许陪玩提前开始**；预约时段**不占用档期**、不拦截其他老板下单，时间协商由双方在 IM 会话中私下进行。
17. **系统播报收口（P1-3）**：**取消充值播报**，只保留送礼播报。
18. **应单未选中处理（P1-4）**：公开派单中应单但未被选中的陪玩，应单记录**自动失效，不做推送提醒**。
19. **合并支付失败处理（P1-5）**：多陪玩订单合并支付时余额不足的，**整单失败、不生成订单**，引导充值后重新支付，不做部分下单。
20. **登录合并与短信服务商（P1-6）**：微信快捷登录与短信验证码登录命中同一手机号时，**按手机号合并账号**（更新补齐账号字段）；短信服务采用**腾讯云短信**。
21. **亲密度与榜单跑批（P1-7）**：退款连带扣减亲密度时**下限为 0，不允许负值**；榜单定时跑批频率与榜单周期同名（如小时榜每小时整点更新、日榜每日零点更新，以此类推），**不做推送，由小程序端自行拉取**。
22. **价格目录口径（P1-8）**：单价维度确认＝**板块 × 陪玩等级 × 模式**；**模式字典按板块单独配置**；**加价项目录为全局配置**。
23. **提现规则（P1-9）**：**起提门槛可配置**；到账方式由陪玩自选，**微信零钱、银行卡均需支持**；提现**必须经后台审核**；一期**不做人工转账回填凭证**。
24. **客服账号建模（P1-10）**：客服是管理后台中**权限级别低于管理员的角色账号**，不建模为特殊普通用户；客服代发派单链接走管理后台权限体系，具体权限由后端代码对 API 分级指定。

## 三、订单状态机（依据第一、二轮澄清推导，2026-11-23 更新）

```
【选人阶段：不产生订单】
  指定单：选陪玩(多人) → 填需求/预约时段 → 知悉须知(留痕) → 星星支付
  公开派单：发布需求(窗口可配,默认120s) → 陪玩应单 → 老板选人 → 填需求 → 知悉须知 → 星星支付
          └─ 超时无人应单 → 派单失效 → 老板可重新发起（应单未中者记录自动失效，不推送）
  客服派单：客服代发派单链接(有效期同公开派单) → 后续同公开派单流程

支付成功 → 按陪玩人数生成 N 条独立订单(同一支付批次号，UI 层合并展示)，状态＝待开始
   （余额不足 → 整单失败、不生成订单，引导充值后重付）
   ├─ 老板主动取消(仅开始前) → 星星原路退款 ──────────────→ 已退款
   ├─ 陪玩「拒绝服务」→ 全额退星星 ───────────────────────→ 已退款
   ├─ 超时未开始 → 老板选择：继续等待(重置计时) / 退星星 ─→ 已退款
   └─ 陪玩点「开始」(预约单允许提前开始) → 服务中
         ├─ 陪玩点「结束」→ 待老板确认
         │     ├─ 老板确认             → 已完成 → 评价(超期未评自动 5 星) → 已评价
         │     └─ 超期未确认(可配天数) → 系统自动确认 → 已完成 →（同上）
         └─ 陪玩失联/中途停止 → 老板申诉客服 → 客服核实 → 后台强制退款(留痕) → 已退款

注：任何退款均连带扣减亲密度(下限 0)；全部状态流转写订单事件日志，客服强制退款记录操作人与原因。
```

### P0 级（不解决会阻断设计）

- [x] **P0-2 老板账号里的星星能否提现/转账？**
  第一轮说"注销前需提现全部星星"，但老板余额来自充值，常规设计不可提现。请明确：老板余额是否允许提现、是否允许老板间转账？注销时余额如何处理（建议：不可提现、不可转账，注销时余额作废并写入用户协议）。

- [x] **P0-3 "注销后数据直接删除"无法落地**
  交易/支付凭证依法需留存（网络日志 ≥6 个月、交易凭证 ≥5 年），且订单、评价、礼物记录均引用用户 ID，物理删除会导致外键悬空、榜单与礼物墙坍塌。建议改为：**账号注销 = 个人信息匿名化 + 置注销标记 + 禁止登录**，业务与财务数据保留。请确认是否接受。

- [x] **P0-4 陪玩钱包需要分子账户**

- [x] **P0-5 状态机三个异常分支的规则**

## 七、需求变更管理约定

### 1. 文档分层与权威性

| 层级 | 文档 | 职责 |
|---|---|---|
| L1 业务基线 | `产品需求.md` | 描述"做什么"，唯一完整需求基线，长期保持最新 |
| L2 决策日志 | `需求澄清记录.md`（本文档） | 记录争议结论与变更原因，带日期/编号/状态 |
| L3 设计产出 | `后端表结构.md`、API 文档等 | 描述"怎么做"，从 L1/L2 推导 |
| 存档 | `project-plan.md` | 已无参考效力，仅历史留存 |

- 决策回流 PRD 之前若发生冲突，权威性顺序：**本文档 > 产品需求.md > 其他衍生文档**。
- 本文档的定位是"变更缓冲区 + 决策日志"，不是长期蓝本；已确认结论须定期回流 PRD（见下）。

### 2. 变更流程

1. **提出**：新疑问/变更在本文档新开一轮（第三轮起），每条分配决策编号（`D-001` 起递增），状态＝`待确认`。
2. **确认**：状态改 `已确认` 并注明日期；同步更新 L3 设计文档，代码提交信息引用编号（示例：`feat(order): #D-012 超时自动退款`）。
3. **回流**：每个模块开工前的里程碑，将已确认决策合并回 `产品需求.md`，作废表述就地标注；合并后本条目标记 `已并入PRD`。
4. **翻案**：已确认决策被新结论替代时，不删除旧条目，新增条目注明"替代 D-xxx"，保留演进历史。

### 3. 纪律

- 任何文档不允许静默修改：修改 PRD 或表结构必须能在本文档追溯到决策编号。
- 每条决策只允许三种状态：`待确认` / `已确认` / `已并入PRD`（被替代的旧条目不删，标注替代关系）。

## 二、技术架构建议

### 2.1 总体形态

一期负载与团队规模下采用**模块化单体**，不引入微服务：一个可部署应用内按业务域分包，定时任务同工程内调度；外部服务通过适配接口隔离，为未来拆分留边界。

### 2.2 推荐技术选型（待评审）

- 主框架：Spring Boot 3 + Java 17（团队若偏好 Node 栈，NestJS + Prisma 亦可承载，架构约定不变）
- 存储：MySQL 8（唯一业务库）+ Redis（缓存/验证码/分布式锁/在线状态/派单 TTL）
- ORM：MyBatis-Plus；数据库迁移：Flyway（建表与变更全部脚本化，禁止手工改库）
- 调度：XXL-JOB 或 ShedLock（保证多实例下任务不重复执行）
- 鉴权：JWT + 注解式 RBAC；接口文档：springdoc OpenAPI
- 可观测：日志规范、资金/回调失败告警、慢查询与基础监控

### 2.3 工程结构（按 L3 八大域分包）

```
common      基座：BaseTable 填充、统一响应、异常、分页、ID 发号器、锁、幂等
config      内容与配置：Plate / TextVersion / NoticeAckLog / Activity / SysConfig
catalog     价格目录：PlaymateLevel / PlateMode / Price / AdditionalItem
user        用户与陪玩：User / Playmate / PlaymatePlate / PlaymateStats /
            ProfileAudit / LoverRelation / AdminUser
dispatch    派单与应单：Dispatch / DispatchApplication
order       订单与评价：Order / OrderEvent / OrderJudge（含状态机、计价引擎）
wallet      钱包资金：Wallet / WalletTransaction / CommissionRecord /
            RechargeOrder / WithdrawOrder（记账内核 + 米大师适配 + 提现审核）
gift        礼物与播报：Gift / GiftRecord / GiftWall / GiftBroadcast
rank        亲密度与榜单：Intimacy / IntimacyLog / RankSnapshot
external    外部适配接口：米大师 / 腾讯云 IM / 腾讯云短信（各含 Mock 实现）
job         定时任务：派单超时、订单超时、自动确认、自动评价、榜单跑批、对账、活动下架
```

### 2.4 API 分组与鉴权

- `/api/app/**`：C 端接口，用户 JWT；游客仅放行公开只读接口（浏览、列表、详情、榜单、播报等）。
- `/api/admin/**`：管理端接口，AdminUser JWT；按 `role`（管理员/客服）做 API 级分级，客服仅放行白名单（代发派单、强制退款等），客服不进入普通 User 体系。
- webhook 独立入口：米大师支付回调、IM 卡片按钮回调，强制验签 + 幂等处理。
- 陪玩一期隐藏老板类能力不能只靠前端：充值、下单、送礼等 API 必须在服务端按身份拦截。

### 2.5 外部服务适配原则

米大师、IM、短信各定义独立接口，业务层只依赖接口；本地与 CI 环境使用 Mock 实现，沙箱/真机配置按环境切换，避免开发被外部环境阻塞。

## 三、分阶段开发计划

总原则：**先内核后业务、先资金后交易；管理端接口与 C 端接口同阶段成对交付；每阶段先出 OpenAPI 契约供前端 Mock 并行。**

|---|---|---|---|---|

| P4 | 陪玩档案与发现 | Tag/资料审核/在线状态/列表筛选/搜索/详情/恋人 | 2 周 | P1、P2 |

### P0 工程基建

**任务**

1. 按《后端表结构.md》逐张建表，Flyway 管理迁移；唯一约束与索引一次建对：phone / wxUnionid / wxOpenid、(plateId,name)、(userId,plateId)、(dispatchId,playmateId)、(giftId,playmateId)、(bossUserId,playmateId)、榜单快照唯一键等。
2. 公共机制：BaseTable 字段自动填充、逻辑启停（不物理删除）、全局异常与统一响应体、参数校验、分页封装、OpenAPI。
3. 系统 ID 发号器：全表共用、从 **10000** 起递增，采用号段模式（发号表或 Redis incr + 偏移量）。
4. SysConfig 服务：键值读取 + Redis 缓存 + 按 valueType 解析；14 个配置键落成常量类，代码禁止硬编码。
5. 定时任务框架、分布式锁、操作日志/审计骨架、两套鉴权过滤器。

**验收**：全表迁移成功；配置读取与缓存生效；未授权请求被两套过滤器正确拦截；发号器在并发下不重号。

### P1 账号与权限

**任务**

1. 微信快捷登录（unionid/openid）与短信验证码登录（腾讯云短信，验证码存 Redis 带 TTL）。
2. **手机号合并主键**：两种登录命中同一 phone 时更新补齐字段、合为同一账号，绝不新建；对唯一约束冲突做兜底处理。
3. JWT 签发与游客模式；注销用户禁止登录。
4. 账号注销：前置校验（无进行中订单；陪玩收入余额须全部提完）→ 个人信息匿名化 + `status=2` + 充值余额作废并写 `CANCEL_INVALID` 流水；业务/财务数据依法留存（网络日志 ≥6 个月、交易凭证 ≥5 年）。
5. AdminUser 与 RBAC：管理员/客服两角色，客服权限注解白名单收敛；加盐哈希存储口令。
6. 隐私设置：隐私号、榜单金额隐藏、榜单匿名、亲密度匿名四个开关；陪玩强制可被搜索（隐私号开关服务端禁用）。

**验收**：同手机号双登录只产生一个账号；注销后不可登录且数据按规留存；客服越权访问 admin 接口被拒。

### P2 内容与价格目录

**任务**

1. 营业板块、陪玩等级、板块模式字典（按板块配置，(plateId,name) 唯一）。
2. 价格表（板块 × 等级 × 模式 → 单价，区分按小时/按局）、全局加价项目录（固定金额、可叠加）。
3. 须知 `TextVersion` 版本化维护；`NoticeAckLog` 知悉留痕接口（按版本锁定、只追加不可篡改）。
4. 活动管理：后台修改实时生效，过期自动下架（读时判断 + 定时任务双保险）；C 端纯展示。
5. 播报开关/频率/条数等配置维护所需的 admin 接口。

**验收**：后台可配齐下单所需全部基础数据；须知新版本发布后旧留痕仍指向旧版本；过期活动 C 端不可见。

### P3 钱包内核 + 充值提现（资金安全第一）

**任务**

1. **统一记账服务（内核先行）**：所有余额变动只允许走单一入口，入参带幂等键（bizType + bizId 唯一）；同事务内完成乐观锁校验 `lockVersion` → 更新余额 → 写 `WalletTransaction`（含变动前后余额）；流水只追加、永不修改。
2. 双账户分户：充值余额（不可提现/不可转账/注销作废）与收入余额（可提现）；陪玩老板类行为在 API 层拦截。
3. 抽佣：订单、礼物两个独立比例配置，逐笔写 `CommissionRecord`（抽佣前总额、比例、平台抽成、陪玩净得）。
4. 充值：米大师下单 → `RechargeOrder`（按平台快照汇率 7/10、人民币金额、通道订单号）→ 回调验签幂等入账；**加主动查单兜底**防回调丢失。
5. 提现：起提门槛校验 → 收款账户信息 AES 加密快照（字段清单待 D-011）→ 后台审核流；驳回时收入余额回冲并写流水；一期不做人工转账凭证回填。
6. 日终对账任务：钱包余额与流水聚合核对、在途资金核对，差异告警。

**验收**：并发扣款零超支；重复回调/重复请求不重复入账；驳回回冲后余额与流水一致；对账任务可人工触发并输出差异。
**前置确认**：D-006（收入入账时点）、D-007（是否仅全额退款）、D-011（收款账户字段）。

### P4 陪玩档案与发现

**任务**

1. 陪玩入驻、考核、升级、Tag 登记/取消（admin）；Tag 取消后对应板块接单**硬拦截**；Tag 与恋人关系变更时若有进行中订单则拦截，漏过的在途订单继续完成。
2. 主页资料审核流：头像/背景图/昵称/个人介绍四项修改入 `ProfileAudit`，驳回保持原内容；审核中不可重复提交。
3. 在线状态：陪玩手动上报，落库 + Redis TTL 兜底。
4. 陪玩列表：默认随机（**随机翻页用固定种子保证分页稳定，禁止每页重新随机函数**）；优质/热门/新人三种排序读 `PlaymateStats`（算分规则待 D-009）；板块、性别、级别、在线状态、音色五维筛选可组合，先过滤后排序、下拉分页。
5. 搜索：昵称模糊 + 系统 ID 精确混合结果；隐私号老板过滤、陪玩始终可搜；按角色跳转陪玩详情/用户主页。
6. 陪玩详情聚合接口：资料、Tag、语音、恋爱状态、礼物墙、评价分页；字段可见性规则固化在后端。
7. 恋人关系：老板发起、陪玩经 IM 卡片确认；双方可解除无冷静期；支持匿名展示；变更拦截规则同上。

**验收**：Tag 取消后下单被硬拦截；筛选组合与排序叠加结果正确；隐私号搜索不可见；资料审核驳回不生效。
**前置确认**：D-009（排序算分规则）。

### P5 订单核心（最复杂模块，拆三个小迭代）

**迭代 1：计价与下单**

1. 计价引擎：服务端重算价格，不信前端报价；总价 = Σ（单价 × 数量）＋ 加价项合计；单价、加价项、须知版本、汇率全部快照（`OrderAdditional` 等）。
2. 支付前强制校验 `NoticeAckLog` 已按当前须知版本留痕。
3. 多陪玩合并支付：一个事务内完成总额校验 → 余额不足直接整单回滚（**不生成任何订单**）→ 扣款 → 按陪玩人数生成 N 条独立订单共享 `orderGroupNo` → 逐条写流水。
4. 指定单板块规则（D-002）：仅 1 名陪玩可改板块且限其已认证板块；2 名及以上板块锁定。

**迭代 2：状态机与异常分支**

1. 显式状态机：六态（待开始/服务中/待确认/已完成/已评价/已退款）＋ 四型退款枚举；禁止裸 update 状态，所有流转走唯一入口并写 `OrderEvent`（操作人角色、前后态、备注）。
2. 待开始分支：老板主动取消、陪玩拒绝（全额原路退充值余额）、超时未开始（`startDeadlineAt` 扫描；继续等待则重置计时；放弃则退款）。
3. 待确认分支：超期自动确认（`confirmDeadlineAt` + 自动确认天数配置）。
4. 客服强制退款：admin 白名单接口，操作人与原因强制留痕。
5. 预约单：允许提前开始；不占档期、不拦截其他下单（不加档期逻辑）。

**迭代 3：评价与退款连锁**

1. 评价：1–5 星 + 文字 + 匿名/公开；不打分默认 5 星；超期自动 5 星并标记 `isAuto`。
2. 退款连锁动作同事务完成：退充值余额 + 亲密度扣减（下限 0，写流水）+ 榜单口径扣减 + 订单事件日志。
3. 订单列表/详情双视角接口（老板侧/陪玩侧按钮与字段不同；陪玩侧仅显抽佣后净得）。

**验收**：覆盖状态机全路径的单元测试；合并支付余额不足零订单残留；四类退款资金与亲密度处理正确；全部流转可在 OrderEvent 审计。
**前置确认**：D-006、D-007、D-008（历史榜单快照是否回改）。

### P6 派单与 IM

**任务**

1. 公开派单：发布即写 `expireAt = now + dispatch.window.seconds`（默认 120 秒），Redis TTL + 定时扫描双保险；按板块 Tag/性别/等级/在线状态筛选目标陪玩，经腾讯云 IM **自定义卡片消息**下发（D-003，不做弹窗、不建本地消息表）。
2. 应单/拒绝写 `DispatchApplication`；老板等待页按响应时间排序展示应单陪玩；窗口超时或选人完成后，未中选记录批量置失效且**不推送任何提醒**。
3. 客服派单：走 `/api/admin` 权限体系，`source=2` 记 `csAdminId`，链接有效期同窗口配置；打开后复用公开派单等待页与 P5 结算支付链路。
4. IM webhook 承接卡片按钮回调（应单接受/拒绝、恋人绑定接受/拒绝），验签幂等。
5. 派单转下单成功后回填 `orderGroupNo`。

**验收**：窗口超时精确失效；离线/后台陪玩回小程序后可在 IM 会话回看派单；未中选无提醒；客服代发全链路留痕。

### P7 礼物、亲密度与播报

**任务**

1. 送礼：一次一种礼物、数量可多个；余额校验与扣款；扣佣后入陪玩收入余额并写抽佣明细；upsert `GiftWall`（累计收到数 + 去重送礼人数，未收到的礼物不建行）。
2. 亲密度：按"老板 + 陪玩"一对 upsert，订单完成与送礼时增加、退款时扣减（**下限 0**），每次变动写 `IntimacyLog`；换算比例读配置。
3. 送礼播报：送礼成功写 `GiftBroadcast`，按频率/条数配置提供前端**轮询接口**（不推送），金额不脱敏；播报语义待 D-012。
4. 送礼记录与公开开关、个人主页消费记录接口。

**验收**：礼物墙人数去重正确；并发送礼亲密度无超扣；播报仅含送礼来源。

**任务**

## 四、横切技术约定（代码评审红线）

1. **资金类操作三要素**：幂等键 + 数据库事务 + 乐观锁；流水不可变，余额必须可由流水重算。
2. **状态流转唯一入口**：订单任何状态变更必须经状态机并落 OrderEvent，禁止绕过。
3. **一切可变参数走 SysConfig**：超时、汇率、抽佣、门槛、文案等改配置即改行为，不发版。
4. **快照原则**：单价、加价项、须知版本、汇率、收款账户一律在业务发生时快照，后台后改不影响历史单据。
5. **外部依赖接口化 + Mock**：米大师/IM/短信业务层只依赖适配接口，CI 全程 Mock。
6. **权限前后端双保险**：游客受限操作、陪玩老板类行为拦截必须在服务端生效，前端隐藏仅为体验。
7. **金额一律整数星星**，人民币仅出现在充值单/提现单；浮点金额用 decimal 类型，禁止 double 记账。
8. **逻辑删除不物理删**：业务数据靠 `enabled`/状态标记，注销仅匿名化。

## 六、文档与协作纪律

1. 遵守既有变更流程：新疑问先进《需求澄清记录.md》拿 D 编号且状态为 `待确认`，确认后回流 PRD/表结构；**代码提交信息引用编号**（示例：`feat(order): #D-006 订单完成时收入入账`）。
2. PRD 与表结构不允许静默修改，任何变更须能追溯到决策编号。
3. 每个领域开工前先产出 OpenAPI 契约并通知前端 Mock，模块交付后接口文档沉淀为 L3 产出。
4. 管理后台界面虽不在原型范围内，但每个域的 admin API 与 app API 同阶段交付，不留尾。
5. 每个阶段完成标志 = 代码合入 + 接口文档更新 + 验收要点通过 + 关键路径测试覆盖。
